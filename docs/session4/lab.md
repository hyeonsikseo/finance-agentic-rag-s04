# 4회차 실습 — Hybrid 검색 · 리랭커 · 필터

수업은 지난 시간과 같이 "강사가 짧게 보여 주고 → 여러분이 직접 채우고 → 테스트로 확인"입니다. 오늘은 채우는 자리가 셋(**실습 1** 하나, **실습 2** 둘)이고, 측정이 둘(**실측 1**, **실습 3**)입니다. 결과물은 `results/hybrid.json` 입니다. 3회차 baseline 과 같은 40문항을 같은 자로 잰 숫자입니다. 아래는 수업 순서대로 적은 것입니다.

**이 문서에서 쓰는 명령**

| 명령 | 하는 일 |
|---|---|
| `make test` | 자동 채점. 2·3회차 검사 35개와 오늘 검사 16개를 한 번에 돌려서 맞으면 초록, 틀리면 빨강 |
| `make bm25-compare` | BM25 만으로 40문항을 풀어 공백 토크나이저와 Kiwi 를 비교한다. 결과는 `results/bm25_whitespace.json`, `results/bm25_kiwi.json` |
| `make hybrid-norerank` | Dense 와 BM25 를 RRF 로 합쳐 40문항. 리랭커 없이. 결과는 `results/hybrid_norerank.json` |
| `make hybrid` | 같은 것에 리랭커까지. **오늘의 결과물** `results/hybrid.json` |
| `make rerank-sweep` | 리랭커 후보 수를 10 · 20 으로 바꿔 가며 문항 10개로 품질과 지연을 잰다. 약 6분 |
| `make check-s04` | 오늘 결과물이 조건 6개를 만족하는지 검사한다. 과제 확인도 이 명령으로 |
| `scripts/search_demo.py` | 질문 하나를 Dense · Hybrid · 리랭커로 검색해 나란히 본다 |

Windows 는 [install.md](../install.md) 의 PowerShell 명령을 씁니다.

## 오늘 끝내고 갈 것

1. Dense 검색이 **놓치는 문항**을 보고 왜 놓치는지 압니다. 임베딩은 뜻이 비슷한 것을 찾지, 글자가 같은 것을 찾지 않습니다.
2. 글자가 같은 것을 찾는 검색(**BM25**)을 한국어에 맞게 만들고, 두 검색의 순위를 **RRF** 로 합칩니다.
3. **리랭커**로 순서를 바로잡고, 후보 수에 따른 품질과 지연을 직접 측정합니다.

## 2부 · BM25 와 한국어 토크나이저

BM25 는 질문의 토큰과 문서의 토큰이 **정확히 같을 때** 점수를 줍니다. 점수는 그 토큰이 문서에 얼마나 자주 나오는가에 그 토큰이 코퍼스에서 얼마나 드문가를 곱한 것입니다. "제31조"는 청크 3,700개 중 몇 개에만 나와서 점수가 크고, "약관"은 거의 모든 청크에 나와서 점수가 거의 없습니다.

문제는 한국어를 공백으로 자르면 토큰이 같아지지 않는다는 것입니다. 셀 3 을 실행하면 같은 문장을 두 방식으로 자른 결과가 나옵니다.

| 공백 분리 | Kiwi 형태소 |
|---|---|
| `제` `15` `조의` `2에` `따른` `중도해지이율은` `연` `1.4%입니다` | `제15조의2` `중도해지이율` `1.4%` `따르` … |

세 가지 규칙입니다. 조항 표기는 `제15조의2` **한 토큰**으로 모읍니다(`normalize_articles` 를 형태소 분석기에 넣기 전에 먼저). 조사·어미(`은`, `에`, `입니다`)는 **떼어 냅니다**. 숫자·비율·금액은 **원형 그대로** 남깁니다. rank_bm25 · fastembed · Qdrant 내장 BM25 모두 한국어 형태소 토크나이저가 없어서 `kiwipiepy` 로 직접 자릅니다. 금융 낱말 23개("중도해지이율", "일부결제금액이월약정" …)는 형태소 분석기가 쪼개지 않도록 사용자 사전에 넣어 두었습니다.

## 실습 1 · `tokenize`

`src/finrag/index/bm25_ko.py` 의 `tokenize` 를 채웁니다. 글을 BM25 토큰 목록으로 만드는 함수이고, 인덱싱할 때와 검색할 때 양쪽에서 씁니다. 8~10줄입니다.

**먼저 읽을 것.** 파일 위쪽의 `KEEP_TAGS`, `NUMERIC`, `ARTICLE_TOKEN`, `_kiwi()`(사용자 사전), `normalize_articles`, `expand_query_terms`, 그리고 `tests/test_hybrid.py` 의 tokenize 테스트 6개. 테스트가 곧 요구사항입니다.

**요구사항.** 테스트 6개가 보는 것입니다. 어떤 재료를 어떤 순서로 쓸지는 직접 정합니다. 순서가 틀리면 어느 테스트가 빨개지는지, 그 메시지가 무엇을 말하는지가 힌트입니다.

1. 조항 표기는 한 토큰으로 모입니다. "제 15 조의 2" 가 `제15조의2` 하나가 되고, `제`·`조의` 같은 토막이 남지 않습니다.
2. 사용자 사전의 낱말(`중도해지이율` 등)은 통째로 한 토큰입니다.
3. 숫자·비율·금액(`1.4%`, `466,666`)은 원형 그대로 남습니다.
4. 조사·어미(`은`, `에`, `입니다`)는 빠지고 내용어만 남습니다. 품사로 거릅니다. Kiwi 토큰은 `.form`(글자)과 `.tag`(품사)를 갖습니다.
5. 빈 문자열이면 빈 목록입니다.
6. `expand=True` 일 때만 별칭 사전(`ALIASES`)의 낱말이 더해집니다. "자기부담금"으로 물어도 "공제금액"이라고 적힌 조항이 걸리게 하는 것입니다. **질의에만** 씁니다. 문서 쪽까지 확장하면 문서마다 없는 낱말이 들어갑니다.

## 실측 1 · 공백 vs Kiwi

```bash
make bm25-compare
```

BM25 **만으로** 골든셋 40문항을 풉니다. Dense 없이, 같은 청크, 다른 토크나이저입니다. 인덱스를 두 번 만들기 때문에 Kiwi 쪽에서 50초쯤 걸립니다. 강사 값입니다.

| 토크나이저 | R@1 | R@5 | R@10 | MRR | 조항번호형 R@5 |
|---|---|---|---|---|---|
| 공백 분리 | 25.0% | 45.0% | 57.5% | 0.334 | 50.0% |
| **Kiwi 형태소** | 30.0% | **62.5%** | **70.0%** | **0.439** | **75.0%** |

어휘가 51,016개에서 8,988개로 줍니다. 같은 낱말이 조사 때문에 수십 가지로 갈라지던 것이 하나로 모였다는 뜻입니다. 여러분 화면(49건)은 Kiwi 쪽이 MRR 0.453 으로 조금 높게 나옵니다. 이 두 줄의 차이가 토크나이저의 값어치이고, 오늘 ADR-003 의 첫 번째 근거입니다. 표를 채팅에 붙여 주세요.

BM25 만으로는 Dense(R@5 75.0%)보다 낮습니다. 그래서 둘 중 하나를 고르지 않고 둘을 합칩니다.

## RRF · 두 순위를 합친다

Dense 가 준 순위와 BM25 가 준 순위는 점수 단위가 다릅니다. 코사인 유사도는 0~1 이고 BM25 점수는 상한이 없습니다. 점수를 정규화해 더하면 어느 쪽이 얼마나 반영되는지가 질문 길이와 코퍼스 크기에 따라 달라집니다. 그래서 점수 대신 **순위**만 씁니다. 순위 r 인 문서에 1/(60 + r) 을 주고, 두 목록에 다 나온 문서는 두 몫을 더합니다.

| 문서 | Dense | BM25 | RRF |
|---|---|---|---|
| A | 1위 | 2위 | 1/61 + 1/62 = 0.0325 |
| C | 3위 | 1위 | 1/63 + 1/61 = 0.0323 |
| B | 2위 | — | 1/62 = 0.0161 |

두 검색이 모두 위로 올린 문서가 앞으로 옵니다. 60 은 관례값입니다. 작을수록 1등이 압도하고, 클수록 순위 차이가 평평해집니다.

## 실습 2 · `rrf` 와 `search` 의 합치기

`src/finrag/retrieval/hybrid.py` 에서 둘을 채웁니다. 합쳐서 15줄 안팎입니다.

**(a) `rrf`.** 순위 목록 여러 개를 받아 `{chunk_id: 점수}` 를 돌려줍니다. 목록마다 순위 r(1부터)인 문서에 `1 / (k + r)` 을 더하고, 여러 목록에 나오면 그만큼 더해집니다. 점수는 쓰지 않습니다. 순위만 씁니다. 테스트 5개.

**(b) `search` 의 합치기.** `dense_hits` 를 받는 줄까지는 있고 그 뒤가 비어 있습니다. Dense 후보의 순위와 BM25 후보(`_bm25().search(...)`)의 순위를 `rrf` 로 합쳐, 점수 내림차순 상위 k 개를 `_hydrate(chunk_id, 점수)` 로 돌려줍니다. 테스트 2개.

생각할 것이 하나 있습니다. **필터(`flt`)가 있을 때 BM25 결과를 그대로 써도 될까요.** Dense 는 Qdrant 안에서 필터를 적용해 돌아오지만, BM25 인덱스는 Qdrant 밖의 메모리에 있어 필터를 모릅니다. 발행사를 카카오뱅크로 걸었는데 BM25 가 하나은행 청크를 올리면 안 됩니다. 두 번째 테스트가 이것을 봅니다. `dense_hits` 의 원소에는 `doc_id` 가 있고, `_by_id()[chunk_id]["doc_id"]` 로 BM25 청크의 문서를 알 수 있습니다.

```bash
make test
```

**50개 전부** 초록이면 됩니다(1개는 `make hybrid` 뒤에 돕니다). 노트북 셀 5 를 다시 실행하면 RRF 장난감 결과가 나옵니다.

```bash
make hybrid-norerank
```

| 지표 | baseline | Dense + BM25 → RRF |
|---|---|---|
| Recall@1 | 40.0% | 35.0% |
| Recall@5 | 75.0% | 75.0% |
| **Recall@10** | 80.0% | **82.5%** |

RRF 는 **후보를 넓히는 장치**입니다. 후보 10에서는 10개 안에 정답이 든 문항이 32개에서 33개로 하나 늘었고, 뒤의 실습 3 표에서 후보를 20으로 늘리면 36개(90%)까지 늘어납니다. 그런데 1등은 오히려 줄었습니다. 두 순위를 섞으면 Dense 가 1등으로 잘 찾던 문항이 2~3등으로 밀리기도 하기 때문입니다. 후보를 넓힌 다음에는 순서를 바로잡는 단계가 필요합니다.

## 리랭커 · 질문과 문서를 함께 읽는다

임베딩(Bi-Encoder)은 질문과 문서를 **따로** 숫자로 만들어 비교합니다. 빠르지만 둘 사이의 관계를 보지 못합니다. 리랭커(Cross-Encoder)는 질문과 문서를 **한 쌍으로** 넣어 점수를 냅니다. 정확하지만 쌍마다 모델을 돌려야 해서 3,700개 전체에는 쓸 수 없고, 앞 단계가 추린 후보 10개에만 씁니다. 모델은 `BAAI/bge-reranker-v2-m3` 이고, 후보 하나를 볼 때 앞 512토큰까지 읽습니다.

질문 하나로 먼저 봅니다.

```bash
.venv/bin/python scripts/search_demo.py "제31조 리볼빙" --hybrid
.venv/bin/python scripts/search_demo.py "제31조 리볼빙" --hybrid --rerank
```

두 번째 명령은 리랭커에 넣은 후보 수와 걸린 시간을 같이 찍습니다. 점수 열이 RRF 점수(0.03 안팎)에서 리랭커 점수로 바뀝니다.

```bash
make hybrid
```

| 지표 | baseline | RRF (후보 10) | RRF + 리랭커 (후보 10) |
|---|---|---|---|
| Recall@1 | 40.0% | 35.0% | **55.0%** |
| Recall@5 | 75.0% | 75.0% | 77.5% |
| Recall@10 | 80.0% | 82.5% | 82.5% |
| MRR | 0.532 | 0.509 | **0.652** |
| 문항당 시간 | 0.4초 | 0.7초 | 10.9초 (리랭커 7.8초) |

유형별 MRR: 조항번호형 0.750 → 0.833, 표수치형 0.694 → 0.806, 복합형 0.557 → 0.800, 계산형 0.167 → 0.600. 메타데이터형은 0.500 → 0.450 로 내려갔습니다.

`results/hybrid.json` 이 오늘의 결과물입니다. 여러분 화면은 문서 49건이라 숫자가 조금 다릅니다. 강사 리허설에서는 MRR 0.681, Recall@1 60.0% 로 강사 값보다 조금 높게 나왔습니다(열화 재현본 2건이 없어서). GPU 가속이 없는 노트북은 문항당 시간이 더 걸립니다. 리랭커 모델이 없으면 "건너뜀"으로 RRF 결과가 저장되는데, 그러면 MRR 이 baseline 보다 낮아서 `check-s04` 의 MRR 항목 두 개가 X 가 됩니다.

## 실습 3 · 후보 수를 바꿔 가며 잰다

```bash
make rerank-sweep
```

리랭커에 넣는 후보 수를 10 · 20 으로 바꿔 가며 문항 10개를 두 번 풉니다. 약 6분입니다. 40문항 전부로 후보 50까지 하면 40분이 넘게 걸려서 문항과 후보를 줄였습니다. 아래는 강사가 40문항 전부로 후보 50까지 잰 값입니다.

| 후보 | R@1 | R@5 | R@10 | MRR | 문항당 | 리랭커만 | 후보당 |
|---|---|---|---|---|---|---|---|
| 10 | 55.0% | 77.5% | 82.5% | 0.652 | 10.9초 | 7.8초 | 777ms |
| 20 | 55.0% | 75.0% | 90.0% | 0.655 | 16.1초 | 13.0초 | 649ms |
| 30 | 55.0% | 75.0% | 87.5% | 0.650 | 20.1초 | 17.2초 | 574ms |
| 50 | 52.5% | 75.0% | 85.0% | 0.634 | 31.2초 | 28.2초 | 563ms |

강사 Mac, 40문항 전부. 후보 10과 20의 MRR 차이는 0.003 으로 40문항에서는 구별되지 않고, 50이면 오히려 내려갑니다. 시간은 후보 수에 비례합니다. 그래서 기본값을 10으로 두었습니다.

후보를 늘리면 정답이 후보 안에 들어올 확률은 오르지만, 리랭커가 틀릴 기회도 늘고, 지연은 후보 수에 비례합니다. 표를 채팅에 붙이고, **자기 노트북에서 고를 후보 수와 이유**를 한 줄 적어 주세요. 그 값은 `.env` 의 `RERANK_CANDIDATES` 로 바꿀 수 있고, 과제 ADR-003 의 "되돌릴 조건"에 쓰입니다. 문항이 10개라 숫자가 거칠게 나옵니다. 절대값이 아니라 후보 수에 따른 기울기를 보는 것입니다. 시간이 남으면 `.venv/bin/python scripts/rerank_sweep.py --candidates 10 20 30` 으로 후보 30 도 재거나(약 11분), `--candidates 10 20 30 50 --limit 0` 으로 40문항 전부를 잴 수 있습니다(40분 넘게 걸립니다).
